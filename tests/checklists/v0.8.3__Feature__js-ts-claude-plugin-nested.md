# Human Test Checklist: `js-ts/claude-plugin`, the nested Claude Code plugin

**Target version:** 0.8.3
**Ships with commit:** v0.8.3: feat(layers): js-ts/claude-plugin -- a Claude Code plugin, nested (TBD until committed)
**Companion automated tests:** `tests/test_layers_js_ts.py::TestJsTsLayer::test_the_claude_plugin_is_nested_with_two_manifests` (the tree, both manifests, the settings' two extra targets and human tags, the metadata, no tokens, the version tool's `--check`, `node --test` when node is on PATH); the manifest and compositions tests cover the new entries (js-ts tries 24 combinations). What no automated test does: install the plugin into Claude Code and see it load. That is yours, and it is the point of the slice.

## What this is

The reason the revival was started: a Claude Code plugin as easy to create as a Python package. `--with claude-plugin` makes the shape you keep for claude-bookmarks and described at the design gate: "we keep the plugin in a SUBFOLDER and have all our tooling external to that so we can keep our plugin very trim and tailored. This also means we have two READMEs one for Github and one for Claude's marketplace". The plugin lives in `plugin/` with its own manifest, one SessionStart hook with a script, `node:test` tests and the marketplace README; the root holds `.claude-plugin/marketplace.json`, the GitHub README and the tooling. `VERSION` is the source; `package.json` and `plugin/.claude-plugin/plugin.json` are kept in step; tags are human (`v0.1.0`). TypeScript is a composition away (`--with claude-plugin,ts`).

## High-Value Verification (~5 minutes)

### HV.1 -- The nested shape

- [ ] **Steps:** in `SCRATCH`: `repokit create my-plugin --with claude-plugin --no-push`; `tree my-plugin /F` or `find my-plugin -not -path '*/.git/*' -not -path '*/scripts/*' -not -path '*/private/*'`.
- [ ] **Expected:** at the root: `.claude-plugin/marketplace.json`, `README.md` (the GitHub one, from the structure), `VERSION`, `package.json` (private, `"test": "node --test"`), `.repokit-common.toml`, `CHANGELOG.md`, `.github/workflows/ci-js-ts.yml`, the vault and tooling; in `plugin/`: `.claude-plugin/plugin.json`, `hooks/hooks.json`, `hooks/scripts/session-start.mjs`, `tests/manifest.test.js`, `README.md` (the marketplace one). No `tsconfig.json`, no `release.yml`. **Judge:** is `plugin/` trim enough? Is anything in it that belongs at the root, or the reverse?

### HV.2 -- The two manifests and the two READMEs

- [ ] **Steps:** read `my-plugin/.claude-plugin/marketplace.json`, `my-plugin/plugin/.claude-plugin/plugin.json`, both READMEs.
- [ ] **Expected:** the marketplace names `my-plugin`, lists one plugin with `"source": "./plugin"`; `plugin.json` has name, displayName, description, version `0.1.0`, author (your name and email), homepage, repository, documentationUrl pointing at `plugin/README.md`, keywords; the plugin README carries the install commands (`/plugin marketplace add ORG/my-plugin`, `/plugin install my-plugin@my-plugin`), a what-it-does section, a what-it-reads-and-writes section. **Judge:** against claude-bookmarks' `plugin.json` (15 keys: `userConfig`, the policy URLs, `types`), is this the right starting set, or should the preset carry the policy URLs as placeholders because the marketplace asks for them?

### HV.3 -- The version tool keeps both manifests, and tags are human

- [ ] **Steps:** in `my-plugin`: `python scripts/repokit-common/sync-versions.py --check`; edit `VERSION` to `0.1.1`; `python scripts/repokit-common/sync-versions.py`; read `package.json` and `plugin/.claude-plugin/plugin.json`; `grep tag-format .repokit-common.toml`.
- [ ] **Expected:** `--check` exits 0; after the bump both manifests say `0.1.1`; `tag-format = "human"`.

### HV.4 -- The tests and the hook script, locally

- [ ] **Steps:** in `my-plugin`: `npm test`; `echo '{"hook_event_name":"SessionStart","source":"startup"}' | node plugin/hooks/scripts/session-start.mjs`; the same with `MY_PLUGIN_DEBUG=1` set.
- [ ] **Expected:** three `node:test` tests pass with no install; the script prints `{}`; with the debug variable it prints a JSON object whose `additionalContext` names the plugin and the event.

### HV.5 -- With TypeScript, and the refusals

- [ ] **Steps:** `repokit create tsp --with claude-plugin,ts --no-push`; `repokit create x --with claude-plugin,node-package --no-push`; `repokit list js-ts`.
- [ ] **Expected:** `tsp/` adds `tsconfig.json` and the ts layer's `package.json` (typescript devDependency, build and typecheck scripts) over the node layer's, and prints the one-line note that `claude-plugin,ts` is not a tested preset; `x/` is refused: `'claude-plugin' and 'node-package' are both a purpose for js-ts; pick one`; `list js-ts` shows `js-ts/claude-plugin = node, claude-plugin` and `claude-plugin` among the purposes without `(planned)`.

## Section 1: the plugin loads in Claude Code (~5 min, the point of the slice)

- [ ] **Steps:** in a Claude Code session: `/plugin marketplace add C:\path\to\SCRATCH\my-plugin` (a local path works for a marketplace); `/plugin install my-plugin@my-plugin`; start a new session (or `/reload-plugins` if available); then `/plugin` to see it listed.
- [ ] **Expected:** the marketplace is added and the plugin installs from `./plugin`; a new session runs the SessionStart hook without error (nothing visible unless the debug variable is set in the environment Claude Code inherits); the plugin appears in the list with the description from `plugin.json`. **Judge:** did anything the marketplace or the installer complains about point at a missing manifest field? Record it as a wish for the preset.
- [ ] **Cleanup:** `/plugin uninstall my-plugin@my-plugin`; `/plugin marketplace remove my-plugin`.

## Section 2: the hooks on the first commit (~1 min)

- [ ] **Steps:** in `my-plugin`: change `plugin/README.md`, `git add -A && git commit -m "change"`.
- [ ] **Expected:** the pre-commit hook passes; the post-commit hook keeps the version stamps in step (both JSON targets) and says nothing about a missing version file.

## What the automated tests DO cover

The tree, both manifests' content, the settings' keys and two extra targets, the metadata, no tokens left, the version tool's `--check`, `node --test` across the plugin's tests, every composition of the js-ts layers assembling cleanly, the refusals of the still-planned flavours.

## What mocks and automation DON'T cover

Installing into Claude Code; the marketplace's view of the manifests; the taste of the manifest's field set against bookmarks'; the hooks on a real commit.

## Reset between sections

Delete the `SCRATCH` projects (`dz safedel` where available); remove the scratch marketplace from Claude Code.

## Cleanup

Remove `SCRATCH`. Nothing outside it is written, except the marketplace registration in Claude Code if Section 1 ran and was not cleaned up.
