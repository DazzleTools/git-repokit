Suite: see the commit.

## What this is

0.7.1 makes `repokit create NAME --language python` produce the shape every project made from git-repokit-template has: a `pyproject.toml` with a dynamic version, a package with a `cli.py` and the hooks' `_version.py`, tests, and the publish-on-release workflow. The automated test proves the generated project installs and tests in a clean venv. What it cannot judge: how the generated project *feels* to start working in -- the names, the first `pip install`, the `--version` line, the release workflow's wording -- and whether it matches a real template-made project.

## High-Value Verification (~5 minutes)

### HV.1 -- A bare Python project is the pypi shape

- [ ] **Steps:** `repokit create my-tool --language python --description "A demo tool" --no-push`
- [ ] **Expected:** `my-tool/pyproject.toml` (with `name = "my-tool"`, `my-tool = "my_tool.cli:main"`, `version-source = "my_tool/_version.py"`), `my-tool/my_tool/{__init__,__main__,cli,_version}.py`, `my-tool/tests/{conftest,test_version}.py`, `my-tool/.github/workflows/release.yml`; `.repokit.json` says `"archetype": "python/pypi"`. No `setup.py`.
- [ ] **Why this matters:** this is what every new Python project is from now on.

### HV.2 -- It installs and its tests pass

- [ ] **Steps:** in `my-tool`: `python -m venv .venv`; activate; `pip install -e . pytest`; `python -m pytest -q`; `python -m my_tool --version`; `my-tool --version`.
- [ ] **Expected:** install succeeds; `7 passed`; both version commands print `my-tool 0.1.0`. Deactivate and delete `.venv` after.
- [ ] **Why this matters:** a generated package that does not install is worse than no package.

### HV.3 -- The old output is one flag away

- [ ] **Steps:** `repokit create demo --archetype python/setuppy --no-push`
- [ ] **Expected:** `demo/setup.py` and `demo/requirements.txt` exactly as 0.7.0's bare `--language python` gave; `.repokit.json` has `"language": "python"` and `"archetype": "python/setuppy"` (0.7.1 fixed `generic` here).

### HV.4 -- The hooks know the generated project

- [ ] **Steps:** in `my-tool` (its hooks are installed by create): edit `README.md`, `git -C my-tool add -A`, commit (scratch-git rules).
- [ ] **Expected:** the pre-commit stamps `my_tool/_version.py`'s `__version__` with branch, build and hash and says `Version updated for commit`; `git -C my-tool log -1 --stat` lists `_version.py`.

### HV.5 -- Several languages: the first one's default archetype, and only that one

- [ ] **Steps:** `repokit create mixed --language c-cpp,python --no-push`, then `repokit create mixed2 --language python,c-cpp --no-push`.
- [ ] **Expected:** `mixed/` has `CMakeLists.txt`, `include/mixed/version.h` and `.repokit-common.toml` naming the header, **no** `pyproject.toml`, and both languages' lines in `.gitignore` (`cmake-build-*/` and `.ruff_cache/`); `.repokit.json` says `"archetype": "c-cpp/cmake-app"`. `mixed2/` has `pyproject.toml` (pypi) and `include/mixed2/version.h`, **no** `CMakeLists.txt`; `"archetype": "python/pypi"`.
- [ ] **Why this matters:** 0.7.0 applied every language's default; pypi's `pyproject.toml` table and cmake-app's `.repokit-common.toml` would both claim the project's settings. Judge whether "first language is primary" reads as the natural rule from `--help` and the README.

## Section 1: against a real template-made project (~5 min)

- [ ] **Steps:** open a project you made from git-repokit-template (dazzlelink, amdead) beside `my-tool`; compare `pyproject.toml`, `_version.py`, `tests/test_version.py`.
- [ ] **Expected:** the same shape and sections; differences are the project's own additions. Judge: is anything the template's setup workflow produced missing here (it produced `__init__.py`, `__main__.py`, `_version.py`; it never produced `cli.py`, which this layer adds)?

## Section 2: wording (~2 min)

- [ ] **Steps:** read the generated `cli.py`, `__init__.py` docstrings and `pyproject.toml` description.
- [ ] **Expected:** the description you passed appears verbatim; the GPL-3.0-or-later license line is what you want for a new project (the template's choice; change the layer if not).

## Section 3: the release workflow (~1 min, read-only)

- [ ] **Steps:** read `my-tool/.github/workflows/release.yml`.
- [ ] **Expected:** byte-identical to git-repokit-template's `release.yml` (publish on a published GitHub Release, trusted publishing, `environment: pypi`); the `if: github.repository != 'DazzleTools/git-repokit-template'` guard is harmless here. CI (`ci.yml`) is not yet in the layer: it arrives with the per-language CI in the next release.

## What the automated tests DON'T cover

- The `my-tool` console script on PATH (HV.2's last command) -- the test runs the module form.
- The pre-commit stamp inside the generated project (HV.4).
- How the generated project compares with a real template-made one (Section 1).
- The license and metadata choices (Section 2).
