# Human Test Checklist: CI from the layers, `.gitattributes`, `CHANGELOG.md`

**Target version:** 0.7.3
**Ships with commit:** v0.7.3: feat: CI per language from the layers; .gitattributes and CHANGELOG in the structure; main.yml gone (TBD until committed)
**Companion automated tests:** 1 new end-to-end test in `tests/test_layers_cli.py` (`test_ci_attributes_and_changelog_follow_the_language`: a Python, a cmake-app and an msbuild project), the generic test extended; suite: see the commit.

## What this is

Since 2025 every project git-repokit made carried git-repokit's **own** CI workflow (`main.yml`, running `mypy repokit/`) and a README whose badge line was the literal word `$badges`. 0.7.3 removes the first and fixes the second: CI now comes from the language layers (`ci-python.yml`, `ci-c-cpp.yml`), the badge names the workflow that exists, and the structure gains `.gitattributes` (line endings, `linguist-vendored` for the vendored tooling) and a `CHANGELOG.md` with the first version's heading. The automated test parses the generated workflows and runs the vendored version tool against the generated changelog. What it cannot see: GitHub actually running the workflows, the language statistics on a pushed repository, and how the README reads.

## High-Value Verification (~5 minutes)

### HV.1 -- A Python project's CI is Python's, and the badge names it

- [ ] **Steps:** `repokit create my-tool --language python --no-push`; list `my-tool/.github/workflows`; read `my-tool/README.md`'s first lines.
- [ ] **Expected:** exactly `ci-python.yml` and `release.yml`; no `main.yml`; `ci-python.yml` has a `test` job running `python -m pytest tests/ -v` on a Python matrix and a `build` job; nothing in it mentions `mypy repokit`. The README's badge line reads `[![GitHub Workflow Status][workflow-badge]][workflow-url]` with `[workflow-badge]: .../actions/workflows/ci-python.yml/badge.svg` -- not the word `$badges`.
- [ ] **Why this matters:** every generated project used to type-check git-repokit instead of itself.

### HV.2 -- `.gitattributes` and the vendored line

- [ ] **Steps:** `type my-tool\.gitattributes` / `Get-Content my-tool\.gitattributes` / `cat my-tool/.gitattributes`.
- [ ] **Expected:** `* text=auto`, the binary extensions, and `scripts/repokit-common/** linguist-vendored`.

### HV.3 -- The changelog and the version tool agree from the first commit

- [ ] **Steps:** in `my-tool`: `python scripts/repokit-common/sync-versions.py` then `python scripts/repokit-common/sync-versions.py --check`.
- [ ] **Expected:** the first run stamps `my_tool/_version.py` (`__version__ ... updated`) and reports `CHANGELOG.md: compare links` in sync or updated; `--check` exits 0 with `All versions are in sync.` `CHANGELOG.md` has `## [Unreleased]`, `## [0.1.0] - <today>`, and two link lines naming your GitHub user and `my-tool`.
- [ ] **Why this matters:** without a `## [0.1.0]` heading the version tool warned on every commit of a new project.

### HV.4 -- C/C++: cmake-app has CI, msbuild has none, and the badge follows

- [ ] **Steps:** `repokit create cm --language c-cpp --no-push`; `repokit create ms --archetype c-cpp/msbuild --no-push`.
- [ ] **Expected:** `cm/.github/workflows/ci-c-cpp.yml` (CMake + CTest on three operating systems) and a `ci-c-cpp.yml` badge in `cm/README.md`; `ms/` has no `.github/workflows` folder and its README has no workflow badge (the version and language badges remain).

### HV.5 -- generic: no CI, still the attributes and changelog

- [ ] **Steps:** `repokit create plain --no-push`.
- [ ] **Expected:** no `.github/workflows`; no workflow badge; `.gitattributes` and `CHANGELOG.md` present.

## Section 1: the README as a reader sees it (~2 min)

- [ ] **Steps:** render `my-tool/README.md` (VS Code preview, or push and read on GitHub).
- [ ] **Expected:** the badges render as images (the workflow badge shows "no status" until the first run); the "Acknowledgements" line carries your git identity, not `Unknown Author`. Judge the badge set: workflow, version (hard-coded `1.0.0` -- a known leftover), Python.

## Section 2: on GitHub (optional, your own throwaway repository)

- [ ] **Steps:** `repokit create my-tool --language python --github --private`-style create (see the README's GitHub section) or push `my-tool` by hand; open Actions.
- [ ] **Expected:** `CI (Python)` runs on the push: the matrix installs the project with `pip install -e ".[dev]"`, runs the 7 generated tests, and the `build` job's `twine check` passes. The repository's language bar shows Python only -- `scripts/repokit-common` is not counted (the `linguist-vendored` line).

## Section 3: on GitHub, C/C++ (optional)

- [ ] **Steps:** push `cm`; open Actions.
- [ ] **Expected:** `CI` runs on windows, ubuntu and macos: vcpkg bootstrap, configure, build, ctest. Record failures on the non-Windows runners as findings (the layer's presets were only ever built on Windows).

## What the automated tests DO cover

| Area | Test | Count |
|---|---|---|
| Python: workflow set, `python -m pytest tests/` present, `mypy repokit` absent, badge names `ci-python.yml`, vendored attribute, `## [0.1.0]`, the version tool syncs then checks clean | `test_ci_attributes_and_changelog_follow_the_language` | 1 (three projects) |
| cmake-app: `ci-c-cpp.yml` with cmake and ctest, badge; msbuild: no workflows, no workflow badge | same test | -- |
| generic: no workflows, no workflow badge, attributes and changelog present | `test_generic_lays_down_no_code_type_files` | 1 |

Red-green (`tests/one-offs/thinking/g5-redgreen/`): the badge not naming the workflow, the vendored line dropped, the changelog heading wrong, the Python CI not running pytest, and the README context losing `badges` again -- each turns the test red.

## What the automated tests DON'T cover

- GitHub running either workflow, and the language bar (Sections 2 and 3).
- The README as rendered (Section 1); the hard-coded `1.0.0` version badge is a known leftover from 2025, not touched here.
- `ci-python.yml` on a `setup.py`-only project (the install step handles it; untested on GitHub).
