## What this is

Through 0.7 a project was a language and one archetype within it (`--archetype python/pypi`). 0.8.0 replaces the single flag with `--with`, a list: a preset (`python/pypi`), a layer qualified by its language (`c-cpp/qt`), or a bare name when only one language has it (`setuppy`). Every layer now has a **facet** in the manifest, the question it answers (runtime, dialect, build, framework, purpose), and the tool orders a list by facet, fills in what a layer implies, refuses two answers to a one-answer question, recognises a list that equals a preset, and notes once when it does not. `repokit list` prints the catalogue. Nothing Python or C/C++ produce changed. What the automated tests cannot see: how the error messages read to a person, whether `repokit list` is legible in a real terminal at its width, whether the help text makes the grammar discoverable, and whether the one-line note on a composition is noticed or ignored.

## High-Value Verification (~6 minutes)

### HV.1 -- The common case is unchanged, and records its layers

- [ ] **Steps:** in `SCRATCH`: `repokit create demo --language python --no-push`; read `demo/.repokit.json`.
- [ ] **Expected:** the same pypi project as 0.7.3 (`pyproject.toml`, `demo/_version.py`, `tests/`, `.github/workflows/ci-python.yml` and `release.yml`); `.repokit.json` has `"archetype": "python/pypi"` and a new `"layers": ["python", "python/pypi"]`.
- [ ] **Why this matters:** the ruling that Python behaviour is never lost; the identity one-off checked bytes, your eyes check the shape.

### HV.2 -- `repokit list` on your terminal

- [ ] **Steps:** `repokit list`; then `repokit list python`; then `repokit list cobol`.
- [ ] **Expected:** one block per language (c-cpp, javascript as planned, python); under each, the presets as `name = layers` with `<- default` on one, planned ones marked `(planned: ...)`; then the facets that have choices (`build one of: ...`, `framework any of: ...`). About 18 lines for the whole catalogue, under 10 for python. `cobol` fails naming the known languages. **Judge:** does the layout survive your terminal width without wrapping the planned descriptions into a mess? Is `one of` / `any of` understood at a glance?

### HV.3 -- Composition: a bare name, the order, the note

- [ ] **Steps:** `repokit create s --with setuppy --no-push`; then `repokit create m --language python --with minimal --no-push`; read both `.repokit.json` files and the second create's output.
- [ ] **Expected:** `s/` is the setup.py project with `"archetype": "python/setuppy"` (a bare name, unique to python, recognised as the preset). `m/` is a two-language project (`setup.py`-less python layer plus the C/C++ minimal build: `main.c`, `Makefile`, `build.bat`); its `.repokit.json` has `"archetype": null` and `"layers": ["python", "c-cpp", "c-cpp/minimal"]`; the create printed exactly one line `Note: assembled from layers; not a tested preset (minimal)` near the end. **Judge:** is the note visible where you look, and worded so you know what to do with it?

### HV.4 -- The refusals, before anything exists

- [ ] **Steps:** `repokit create x --with pypi,setuppy --no-push`; `repokit create x --with qt --no-push`; `repokit create x --with pypii --no-push`; `repokit create x --with python/django --no-push`; then `dir x` / `ls x`.
- [ ] **Expected:** four failures, no `x/` folder: `'pypi' and 'setuppy' are both a build for python; pick one`; `'qt' is ambiguous: c-cpp/qt or python/qt`; `unknown name 'pypii'; known: ...; did you mean pypi?`; `archetype python/django is not built yet: a Django project`. **Judge:** each message tells you what to type instead.

### HV.5 -- The old flag is gone

- [ ] **Steps:** `repokit create x --archetype python/pypi --no-push`; `repokit create --help | more`.
- [ ] **Expected:** argparse refuses `--archetype` (`unrecognized arguments`); the help shows `--with NAME[,NAME...]` with its examples and points at `repokit list`; `--language` still lists the known languages.

### HV.6 -- adopt takes the same list

- [ ] **Steps:** make a folder with a `README.md` of your own and `git init` it (scratch); `repokit adopt . --with c-cpp/minimal --no-push` (or the adopt form your 0.7 checklist used).
- [ ] **Expected:** the minimal layer's files appear beside yours; your `README.md` is untouched (preserve mode); `.repokit.json` records the layers.

## What the automated tests DO cover

The eight resolver rules on a mock manifest with js-ts entries (so AC-3 and AC-7 are pinned before js-ts exists); the facet/layer tables against the shipped layer folders; the CLI's refusals, the note count, the metadata's `layers`, the `list` command's size and content; every composition of the shipped layers assembling without a same-path collision or a surviving token; byte identity with v0.7.3 for five requests; the audit that each new test goes red when its rule is removed.

## What mocks and automation DON'T cover

The error messages as read by a person at a terminal; `repokit list` at real terminal widths and with color themes; the discoverability of `--with` from `--help` alone; whether the one-line note is noticed; `adopt` against a real project with its own files; the README's vocabulary for someone outside this project.

## Reset between sections

Delete the `SCRATCH` projects (`dz safedel` where available). Nothing outside `SCRATCH` is written.

## Cleanup

Remove `SCRATCH`. No global state is touched: `repokit create` writes only under its target folder and reads `REPOKIT_COMMON_SOURCE` from your environment.

## Legend

- **preset** -- a named, tested list of layers: the `[archetypes]` table; `--with python/pypi`.
- **layer** -- one folder under `repokit/templates/layers/archetypes/<lang>/<name>` with a `[layers]` entry naming its facet.
- **facet** -- the question a layer answers: runtime, dialect, build, framework, purpose; one answer per language when exclusive.
- **the note** -- `Note: assembled from layers; not a tested preset (...)`, printed once when a list equals no preset.
