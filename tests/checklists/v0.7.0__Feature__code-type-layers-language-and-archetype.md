# Human Test Checklist: code-type layers -- `--language` as a list, `--archetype`

**Target version:** 0.7.0
**Ships with commit:** v0.7.0: feat: code-type layers -- `--language` list, `--archetype`, one byte-preserving renderer (TBD until committed)
**Companion automated tests:** 22 new in 144 passed / 13 skipped / 1 xfailed -- `tests/test_layers.py` (17: the renderer's two dialects and byte preservation, the manifest, the walk, the settings merge, the wheel), `tests/test_layers_cli.py` (5: real `repokit create` runs)

## What this is

0.7.0 adds the second of git-repokit's two template systems. The structure every project gets is unchanged; `--language` and `--archetype` lay the code type on top from a manifest-driven tree of layers. The automated tests drive the engine on fixture trees and run the real CLI into a temp folder. What they cannot see is what this list is for: how the failures read on a console, path tokens on Windows paths, a generated Python project actually installing, `adopt` on a real messy project, and the private-branch model's settings merge in a real worktree layout. Building the generated C/C++ projects is the next slice's checklist, not this one.

## Prerequisites

1. git 2.30+, Python 3.11+ (`tomllib`), and git-repokit installed from this checkout (`pip install -e .`), or run it as `python -m repokit.cli` from the checkout. `repokit --version`-equivalent: `python -c "from repokit.__version__ import __version__; print(__version__)"` prints `0.7.0`.
2. A git-repokit-common checkout for vendoring without the network, or vendoring switched off. Set one of:

   **cmd.exe** -- `set REPOKIT_COMMON_SOURCE=C:\code\git-repokit-common` or `set REPOKIT_COMMON_SOURCE=off`
   **PowerShell** -- `$env:REPOKIT_COMMON_SOURCE = "C:\code\git-repokit-common"` or `"off"`
   **POSIX** -- `export REPOKIT_COMMON_SOURCE=/path/to/git-repokit-common` or `off`
3. A scratch folder, `SCRATCH`, and every `repokit create` below run **from inside it** (create makes `SCRATCH/NAME`):

   **cmd.exe** -- `set SCRATCH=%TEMP%\rk-0.7.0-check && mkdir %SCRATCH% && cd %SCRATCH%`
   **PowerShell** -- `$env:SCRATCH = "$env:TEMP\rk-0.7.0-check"; New-Item -ItemType Directory -Force $env:SCRATCH | Out-Null; Set-Location $env:SCRATCH`
   **POSIX** -- `export SCRATCH=/tmp/rk-0.7.0-check && mkdir -p "$SCRATCH" && cd "$SCRATCH"`
4. **Scratch-git rules.** `repokit create` commits inside the project it makes, with its own identity settings; any git command you run yourself below carries `-C <scratch path>` and `-c user.email=t@example.invalid -c user.name=t -c commit.gpgsign=false -c tag.gpgsign=false`, so nothing lands in a real repository and no GPG dialog opens (on a machine with `commit.gpgsign = true` globally a bare `git commit` would). Never change global git config for this list. `--no-push` on every create: nothing reaches GitHub.
5. **Reset between sections:** delete the created project (`rmdir /s /q NAME` / `Remove-Item -Recurse -Force NAME` / `rm -rf NAME`) and create again. Nothing outside `SCRATCH` is written except where Section 7 says so.

## High-Value Verification (~5 minutes)

### HV.1 -- A Python project is what it was, plus Python's ignore lines

Validates: the gate's "never lose Python behaviour"; the vault's lines survive the layers.

- [ ] **Steps:** `repokit create demo --language python --no-push`
- [ ] **Expected:** `demo/setup.py` has `name="demo"` and an `author=` line from your git identity; `demo/requirements.txt` is the four-line dev list (pytest, black, flake8, mypy); `demo/.gitignore` contains `__pycache__/` **and** `/private/` **and** `CLAUDE.local.md`; `git -C demo status --porcelain` is empty apart from `.repokit.json` (as before 0.7.0).
- [ ] **Why this matters:** every Python project made before 0.7.0 came out this way; the layers must not change it.

### HV.2 -- Two languages stack, in order, with path tokens resolved

Validates: the walk, `.rkappend`, tokens in paths.

- [ ] **Steps:** `repokit create demo --language python,c-cpp --no-push`
- [ ] **Expected:** `demo/setup.py`, `demo/CMakeLists.txt`, `demo/include/demo/version.h` (the folder is `demo`, not `__RK_SNAKE__`), `demo/src/app.rc`, `demo/vcpkg.json` all exist; `demo/.repokit-common.toml` holds `version-source = "include/demo/version.h"` and an `[[tool.repokit-common.extra-targets]]` block for `vcpkg.json`; `demo/.github/workflows/ci.yml` is byte-identical to `repokit/templates/layers/archetypes/c-cpp/cmake-app/.github/workflows/ci.yml` in this checkout (`fc /b` / `Compare-Object (Get-Content ...)` / `cmp`).
- [ ] **Check:** no token left: `findstr /s "__RK_" demo\*` / `Select-String -Path demo\* -Pattern "__RK_" -Recurse` / `grep -r "__RK_" demo` finds nothing (ignore `scripts/repokit-common`).
- [ ] **Why this matters:** this is the engine's whole job; a token left in a file name or a workflow is the visible failure.

### HV.3 -- An unknown or unbuilt name stops before anything exists

Validates: the failure message and that no folder is created.

- [ ] **Steps:** run each: `repokit create demo --language cobol --no-push`; `repokit create demo --language javascript --no-push`; `repokit create demo --archetype python/django --no-push`.
- [ ] **Expected:** each exits non-zero; the messages read `unknown language 'cobol'; known: generic, c-cpp, javascript, python`, `language javascript is not built yet: planned as the js-ts layer ...`, `archetype python/django is not built yet: a Django project`; **no `demo` folder exists** after any of them (`dir demo` / `Test-Path demo` / `ls demo` fails).
- [ ] **Why this matters:** a half-made project after a typo is worse than a refusal.

### HV.4 -- An archetype implies its language and the Visual Studio files share a GUID

- [ ] **Steps:** `repokit create demo --archetype c-cpp/msbuild --no-push`
- [ ] **Expected:** `demo/demo.sln` and `demo/demo.vcxproj` exist (path tokens), the same `{XXXXXXXX-XXXX-...}` project GUID appears in both, `demo/.repokit.json` has `"languages": ["c-cpp"]` and `"archetype": "c-cpp/msbuild"`. Open the `.sln` in Visual Studio if available: it loads the project.
- [ ] **Why this matters:** a GUID that differs between the two files is a solution that cannot find its project.

### HV.5 -- Generated files are LF on Windows

Validates: U2.0b, the byte-for-byte renderer.

- [ ] **Steps (Windows):** after HV.1, `python -c "print(open('demo/README.md','rb').read().count(b'\r\n'))"`.
- [ ] **Expected:** `0`. Before 0.7.0 this was the line count. The generated project's own git normalises either way; what matters is that the bytes no longer depend on the platform that ran `repokit`.
- [ ] **Why this matters:** determinism across machines was the design's stated reason for the change; this is the one-line check of it.

## Section 1: the CLI surface (~5 min)

### 1.1 Help lists the known names

- [ ] **Steps:** `repokit create --help`
- [ ] **Expected:** `--language LANG[,LANG...]` with `Known: generic, c-cpp, javascript, python`; `--archetype LANG/NAME` with the archetype list and "each language has a default". Judge: is the help readable at 80 columns? Does `javascript` appearing in "Known" while being a stub confuse? (It is listed on purpose: naming it tells you it is planned.)

### 1.2 Repeated flags equal a comma list

- [ ] **Steps:** `repokit create demo --language python --language c-cpp --no-push`, then compare `.repokit.json` with HV.2's.
- [ ] **Expected:** `"languages": ["python", "c-cpp"]` both ways; the same files.

### 1.3 generic adds nothing

- [ ] **Steps:** `repokit create demo --no-push`
- [ ] **Expected:** no `setup.py`, `requirements.txt` or `CMakeLists.txt`; `.repokit.json` has `"languages": ["generic"]` and `"archetype": null`.

### 1.4 An unknown archetype names the known ones

- [ ] **Steps:** `repokit create demo --archetype python/nope --no-push`
- [ ] **Expected:** `unknown archetype 'python/nope'; known: c-cpp/cmake-app, c-cpp/cmake-lib, ...` (sorted), exit non-zero, no folder.

## Section 2: the Python project in use (~5 min)

### 2.1 setup.py installs

- [ ] **Steps:** in HV.1's project: `python -m venv .venv`, activate it, `pip install -e .`.
- [ ] **Expected:** installs (an empty package; `find_packages()` finds none, pip still succeeds). Deactivate and delete `.venv` after.

### 2.2 The ignore file in practice

- [ ] **Steps:** `python -c "import demo"`-style noise is not needed: create `demo/__pycache__/x.pyc` and `demo/private/notes.md`; `git -C demo status --porcelain`.
- [ ] **Expected:** neither appears.

## Section 3: adopt (~5 min)

### 3.1 adopt never overwrites

- [ ] **Steps:** make a folder with your own `setup.py` (one line, `# mine`) and `README.md`; `git -C it init -q -b main`, commit (scratch-git rules); then `repokit adopt . --language python --no-push` from inside it (add `--publish-to`-free flags as `adopt --help` shows).
- [ ] **Expected:** your `setup.py` still reads `# mine`; `requirements.txt` was added (it did not exist); `.gitignore` gained the Python lines **after** your own content.

## Section 4: the private-branch model and the settings merge (~5 min)

### 4.1 Both the layer's keys and git-repokit's keys are present

- [ ] **Steps:** `repokit create demo --branch-strategy simple --with-common --language c-cpp --no-push`
- [ ] **Expected:** in `demo/local/.repokit-common.toml` (the private branch's worktree): `version-source = "include/demo/version.h"` **and** `private-patterns = [...]` both present under one `[tool.repokit-common]` header, the header appearing once. Before 0.7.0 one of them would have been lost.
- [ ] **Check:** commit `CLAUDE.md` on `main` (the `github/` worktree): refused by repokit-common's pre-commit; on `local`: allowed.

## Section 5: the package (~3 min)

### 5.1 The wheel carries the layer tree

- [ ] **Steps:** from the checkout: `python -m build --wheel --outdir %TEMP%\rk-wheel` / `$env:TEMP\rk-wheel` / `/tmp/rk-wheel`; then `python -c "import zipfile,glob; n=zipfile.ZipFile(glob.glob('<outdir>/*.whl')[0]).namelist(); print(sum('templates/layers/' in x for x in n), any(x.endswith('.gitignore.rkappend') for x in n), any('.github/workflows/ci.yml' in x for x in n))"`.
- [ ] **Expected:** a count of at least 22, then `True True`.
- [ ] **Check:** no `pip/` or `build/` folder is left in the checkout afterwards (`git status --short` shows neither).

## Section 6: console and wording (~3 min)

- [ ] **Steps:** run HV.3's three failures on a cmd.exe console and on a UTF-8 terminal.
- [ ] **Expected:** the messages render without `?` boxes; the quoted names are readable. Judge: does `is not built yet: planned as the js-ts layer ...` tell you what to do instead? Would `--language javascript` be better off silently treated as generic? (The gate chose the refusal.)

## Section 7: this checkout (~1 min, read-only)

- [ ] **Steps:** from the checkout: `git ls-files --eol repokit/templates | findstr /v "i/lf w/lf"` / `... | Select-String -NotMatch "i/lf w/lf"` / `... | grep -v "i/lf w/lf"`.
- [ ] **Expected:** nothing: every template is LF in the index and in the working tree (`.gitattributes` pins them). A commit in this checkout prints no version warning (`versioning = "off"`; needs the vendored git-repokit-common at 0.4.0 or later).

## What the automated tests DON'T cover

- How the refusals read on a real console, and whether listing a stub under "Known" helps or confuses.
- Path tokens on Windows paths with spaces or non-ASCII characters in the project name (the tests use `demo`).
- A generated Python project actually installing (2.1), and the generated C/C++ projects building (the next slice's checklist).
- `adopt` on a real, messy project (3.1 uses a two-file fixture).
- The private-branch model's merge in a real worktree layout as a person uses it (4.1).
- Visual Studio opening the generated `.sln` (HV.4).

## Reporting issues found

1. Note the section and step number.
2. Capture the exact command and its full output.
3. Keep the created project folder (zip `SCRATCH/demo`).
4. File an issue on DazzleTools/git-repokit referencing this checklist and the 0.7.0 commit.
