# Human Test Checklist: git-repokit ready for PyPI

**Target version:** 0.9.8
**Ships with commit:** `v0.9.8: build(pypi): git-repokit ready for PyPI; Python 3.10 floor; PEP 639 licenses`
**Companion automated tests:** `tests/test_packaging.py` (6), `tests/test_readme_blocks.py` (license tokens), `tests/test_github_owner.py` (the created pyproject's license fields); the full suite on 3.13 and on 3.10.

## What this is

0.9.8 makes git-repokit installable from PyPI as `git-repokit` and gives created Python projects the current license fields. The tests check the files; this checklist covers what only a real run shows: CI's first Linux leg, a real publish through the trusted publisher, and installing from PyPI.

## Planning lineage

**Public:** `CHANGELOG.md` [0.9.8].

**Project-private** (not in public git history, for project maintainers):
- the PyPI row of the open-loops board: the floor measurements, the names, the order, what ships

## Prerequisites

1. The pending trusted publisher on PyPI for `git-repokit` (owner DazzleTools, repository git-repokit, workflow `publish.yml`, environment `pypi`).
2. The `pypi` environment on DazzleTools/git-repokit (Settings > Environments).
3. This version pushed to `main`.
4. On this machine, the editable install is registered under the old name. Swap it once (same in every shell):
   ```
   pip uninstall repokit
   pip install -e .
   ```

## High-Value Verification

### HV.1 -- CI is green on Linux and Windows, 3.10 to 3.13

- [ ] **Steps:** after the push, `gh run list -R DazzleTools/git-repokit --limit 3`, then `gh run view <id>`.
- [ ] **Expected:** eight test jobs (two systems, four Pythons) and the package job pass.
- [ ] **Why this matters:** the Linux leg has never run; a Windows-only assumption in a unit test shows up here first.

### HV.2 -- The local build is clean

- [ ] **Steps** (same in every shell, from the repository root):
  ```
  python -m build --outdir dist/
  python scripts/check_dist_no_leak.py dist/
  python -m twine check --strict dist/*
  ```
- [ ] **Expected:**
  - `git_repokit-0.9.8.tar.gz` and `git_repokit-0.9.8-py3-none-any.whl`;
  - `PASS: 2 artifact(s) clean.`;
  - `PASSED` for both.
- [ ] **Clean up:** remove `dist/`, `build/` and `git_repokit.egg-info/`, since the build writes them into the checkout:
  - cmd.exe: `rmdir /s /q dist build git_repokit.egg-info`
  - PowerShell: `Remove-Item -Recurse -Force dist, build, git_repokit.egg-info`
  - POSIX: `rm -rf dist build git_repokit.egg-info`

### HV.3 -- The first real publish

- [ ] **Steps:** cut the GitHub Release for this version (`/github-release`), then watch the "Publish to PyPI" run.
- [ ] **Expected:**
  - the build job passes the leak check and `twine check`;
  - the publish job runs in the `pypi` environment and uploads;
  - `https://pypi.org/project/git-repokit/` shows 0.9.8, license MIT, requires Python >=3.10.
- [ ] **Why this matters:** this run is what creates the PyPI project. Until it happens, the name is not held.

### HV.4 -- Installing from PyPI

- [ ] **Steps:** in a fresh venv on Python 3.10: `pip install git-repokit`, then `repokit --version`, then a `repokit create demo --language python --license mit --no-push` in a scratch folder.
- [ ] **Expected:**
  - `RepoKit 0.9.8`;
  - `tomli` is installed alongside on 3.10 (`pip show tomli`);
  - the create succeeds, and its `pyproject.toml` says `license = "MIT"` and `license-files = ["LICENSE"]`.
