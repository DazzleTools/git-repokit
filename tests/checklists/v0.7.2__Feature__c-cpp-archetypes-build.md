**Target version:** 0.7.2
**Ships with commit:** v0.7.2: feat: the C/C++ archetypes proven through repokit create (TBD until committed)
**Companion automated tests:** `tests/test_layers_c_cpp.py` (6: the two stubs, the bytes of `app.rc` and `version.h`, cmake-app configure+build+ctest, msbuild, minimal with `cl`, and `sync-versions --check` on the header -- the last skips until the vendored git-repokit-common is 0.4.0). Suite: see the commit.

## What this is

0.7.0 shipped the C/C++ layer files; 0.7.2 proves that what `repokit create` writes actually builds, with the toolchain a Windows developer has. The automated tests run the real builds with Visual Studio 2022's bundled CMake, vcpkg and MSBuild. What they cannot see: a build on a machine with a different VS edition or version (vswhere here reports a VS 18 install beside 2022), Linux and macOS (the CMake presets and the `Makefile` are untested there), the generated project's first real commit through the hooks, and whether the generated `.sln` opens cleanly in the IDE.

## Prerequisites

As the v0.7.0 checklist (git, Python 3.11+, git-repokit from this checkout, `REPOKIT_COMMON_SOURCE`, a `SCRATCH` folder you run from, scratch-git rules, `--no-push` on every create). Plus: Visual Studio 2022 Community/Professional/Enterprise with the "Desktop development with C++" workload (its CMake, vcpkg and MSBuild); set `VS_ROOT` if it is not under `C:\Program Files\Microsoft Visual Studio\2022\<edition>`. Define `VS` as that folder in your shell. The builds write only inside the created project (`build/`, `x64/`).

## High-Value Verification (~10 minutes, mostly build time)

### HV.1 -- cmake-app: configure, build, test, run

- [ ] **Steps:** `repokit create my-tool --language c-cpp --no-push`, then from inside `my-tool`, with `VCPKG_ROOT` set to `VS\VC\vcpkg`:

  **cmd.exe**
  ```cmd
  set VCPKG_ROOT=%VS%\VC\vcpkg
  "%VS%\Common7\IDE\CommonExtensions\Microsoft\CMake\CMake\bin\cmake.exe" --preset windows-release
  "%VS%\Common7\IDE\CommonExtensions\Microsoft\CMake\CMake\bin\cmake.exe" --build --preset windows-release
  "%VS%\Common7\IDE\CommonExtensions\Microsoft\CMake\CMake\bin\ctest.exe" --preset windows-release
  build\Release\my-tool.exe --version
  ```
  **PowerShell**
  ```powershell
  $env:VCPKG_ROOT = "$env:VS\VC\vcpkg"
  & "$env:VS\Common7\IDE\CommonExtensions\Microsoft\CMake\CMake\bin\cmake.exe" --preset windows-release
  & "$env:VS\Common7\IDE\CommonExtensions\Microsoft\CMake\CMake\bin\cmake.exe" --build --preset windows-release
  & "$env:VS\Common7\IDE\CommonExtensions\Microsoft\CMake\CMake\bin\ctest.exe" --preset windows-release
  .\build\Release\my-tool.exe --version
  ```
  **POSIX (Git Bash on Windows)**
  ```bash
  export VCPKG_ROOT="$(cygpath -w "$VS/VC/vcpkg")"
  "$VS/Common7/IDE/CommonExtensions/Microsoft/CMake/CMake/bin/cmake.exe" --preset windows-release
  "$VS/Common7/IDE/CommonExtensions/Microsoft/CMake/CMake/bin/cmake.exe" --build --preset windows-release
  "$VS/Common7/IDE/CommonExtensions/Microsoft/CMake/CMake/bin/ctest.exe" --preset windows-release
  ./build/Release/my-tool.exe --version
  ```
- [ ] **Expected:** configure prints `my-tool version 0.1.0` (read from `include/my_tool/version.h`); build and ctest exit 0 (`100% tests passed`); `--version` prints `my-tool 0.1.0 (0.1.0_main_1-<date>-<hash>)` -- the stamp carries the project's own first commit, never an outer repository's.
- [ ] **Why this matters:** this is the default C/C++ project; if it does not build, the layer is decoration.

### HV.2 -- msbuild: the solution builds and opens

- [ ] **Steps:** `repokit create my-tool --archetype c-cpp/msbuild --no-push`; `"%VS%\MSBuild\Current\Bin\MSBuild.exe" my-tool.sln -nologo -v:minimal -p:Configuration=Release -p:Platform=x64`; `x64\Release\my-tool.exe --version`. Then open `my-tool.sln` in Visual Studio.
- [ ] **Expected:** build exit 0; `my-tool 0.1.0`; the IDE loads the solution and shows the `my-tool` project (the `.sln` and `.vcxproj` share a GUID).

### HV.3 -- minimal: rc + cl

- [ ] **Steps:** `repokit create my-tool --archetype c-cpp/minimal --no-push`; open a "x64 Native Tools Command Prompt for VS 2022" (or `call "%VS%\VC\Auxiliary\Build\vcvars64.bat"`), `cd` into `my-tool`, run `.\build.bat`; then `build\my-tool.exe --version`.
- [ ] **Expected:** `rc` and `cl` run; `my-tool 0.1.0`. Judge: does `build.bat`'s output read clearly? Does it say where the binary went?

### HV.4 -- the stubs

- [ ] **Steps:** `repokit create demo --archetype c-cpp/cmake-lib --no-push`; `repokit create demo --archetype c-cpp/qt --no-push`.
- [ ] **Expected:** each refuses with `archetype c-cpp/<name> is not built yet: ...` and no `demo` folder exists.

### HV.5 -- a version bump reaches the build

- [ ] **Steps:** in HV.1's project, edit `include/my_tool/version.h`: `PATCH 0` -> `PATCH 1` and `STRING "0.1.0"` -> `"0.1.1"` (or, once the vendored git-repokit-common is 0.4.0: `python scripts/repokit-common/sync-versions.py --bump patch`); rebuild (`cmake --build --preset windows-release`); `build\Release\my-tool.exe --version`; in PowerShell `(Get-Item build\Release\my-tool.exe).VersionInfo.FileVersion`.
- [ ] **Expected:** `0.1.1` from the binary and from the Windows VERSIONINFO, with no edit to `app.rc` or `CMakeLists.txt`.

- The hooks inside the generated project with the 0.4.0 copy (Section 1), until that copy is committed and vendored.
