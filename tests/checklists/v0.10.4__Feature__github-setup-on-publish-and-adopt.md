# Human Test Checklist: the GitHub setup on publish, adopt and create --publish-to

**Target version:** 0.10.4
**Ships with commit:** v0.10.4: feat(github): the GitHub setup runs wherever repokit publishes (TBD until committed)
**Companion automated tests:** 32 in `tests/test_github_setup_publish.py` (new), 12 in `tests/test_github_setup.py` (one expectation changed: a repository with only the Roadmap at #1 now gets Quick Notes at #2), plus `tests/test_github_create.py` and `tests/test_github_owner.py` unchanged. Every one of them answers for `gh` with a fake or a stub; none reaches GitHub.

## What this is

Until 0.10.4 the GitHub setup (the house labels, the Roadmap and Quick Notes as issues #1 and #2, the pins, Discussions, topics) ran only inside `repokit create --github`. A project created locally and pushed later with `repokit publish` got none of it. 0.10.4 runs the setup wherever repokit puts a project on GitHub, and `repokit publish` on a project that is already on GitHub sets it up without creating anything. This checklist is for a person to confirm the parts the stubs cannot: real GitHub numbering, real `gh` and token interplay, the interactive prompt in a real terminal.

## Prerequisites

1. git-repokit 0.10.4 installed (`repokit --version`), `gh` installed and logged in (`gh auth status`), a GitHub token for the `--publish-to` route: `GITHUB_TOKEN`, the credentials file, or `--token-command "gh auth token"` on each publish (the form used below; it reads gh's own login).
2. A scratch folder. Every command below runs inside it; nothing touches a real project.
3. **The live sections create one PRIVATE repository under your own account, named `repokit-setup-check`.** You delete it at the end (Cleanup). A tester agent must never delete it.
4. Scratch-git rule: every git command carries `-C <scratch path>`, and every commit carries `-c user.email=t@example.com -c user.name=T -c commit.gpgsign=false`. Never change global git config for this checklist.
5. A global `~/.repokit/config.json` with a `github_setup` list is assumed for HV.1 (for example `["labels", "issues", "pin", "discussions", "topics"]`). If yours has none, add `--github-setup labels,issues,pin,discussions` to the publish commands.

**Make the scratch folder** (pick your shell):

**cmd.exe**:
```cmd
mkdir %TEMP%\rk-0104 && cd /d %TEMP%\rk-0104
```

**PowerShell**:
```powershell
New-Item -ItemType Directory -Force "$env:TEMP\rk-0104" | Out-Null; Set-Location "$env:TEMP\rk-0104"
```

**POSIX**:
```bash
mkdir -p /tmp/rk-0104 && cd /tmp/rk-0104
```

## High-Value Verification (~10 minutes, live)

### HV.1 -- publish of a local project runs the setup before the first push

Validates: the token route creates the repository, the setup runs in the window before the push.

- [ ] **Steps** (same in every shell):
  1. `repokit create repokit-setup-check --language generic --license mit`
  2. `repokit publish repokit-setup-check --publish-to github --private-repo --token-command "gh auth token"`
- [ ] **Expected:**
  - Exit 0; a `GitHub:` line per step: `labels: created ...`, `issues: #1 Roadmap`, `issues: #2 Quick Notes -- Bugs, Features, Ideas`, `pin: #1 pinned`, `pin: #2 pinned`, `discussions: on`, `topics: none named (--topics a,b)`, then the reminders (CI, Sponsorships if the funding extra is on, Pages).
  - `gh issue list -R <you>/repokit-setup-check --state all` shows exactly #1 Roadmap and #2 Quick Notes; both pinned on the repository page.
- [ ] **Why this matters:** this is the exact gap that left a published mod repository with no #1/#2.

### HV.2 -- publish again: the update path creates nothing and repeats nothing

- [ ] **Steps:** `repokit publish repokit-setup-check --publish-to github --no-push`
- [ ] **Expected:** exit 0; nothing created (with `-v` a line reads `... already exists: pushing and updating, nothing created`); `labels: all already there`, `issues: Roadmap and Quick Notes already there`, `pin: #1 already pinned`, `pin: #2 already pinned`. No second repository (no `repokit-setup-check-1`), `origin` unchanged (`git -C repokit-setup-check remote -v`).
- [ ] **Why this matters:** publish is now also the way to bring an existing repository up to the house setup; a second run must be harmless.

### HV.3 -- a pull request at #1 is seen, and the default is to skip

- [ ] **Steps:**
  1. Delete the two issues' effect by making a fresh repository: `repokit create repokit-setup-check-pr --language generic --license mit`, then `repokit publish repokit-setup-check-pr --publish-to github --private-repo --no-github-setup --token-command "gh auth token"`.
  2. Open one pull request on it (any branch, any change) so #1 is a pull request.
  3. In a non-interactive context, `repokit publish repokit-setup-check-pr --publish-to github --no-push --github-setup issues` with `REPOKIT_INTERACTIVE=0` (cmd: `set REPOKIT_INTERACTIVE=0`; PowerShell: `$env:REPOKIT_INTERACTIVE = "0"`; POSIX: `export REPOKIT_INTERACTIVE=0`).
- [ ] **Expected:** `issues: #1 is already pull request '<title>', so Roadmap and Quick Notes would not be #1 and #2; not created`. No issue created.
- [ ] **Why this matters:** issues and pull requests share one number sequence; the old check counted issues only.

### HV.4 -- gh not ready: the publish still completes

- [ ] **Steps:** `gh auth logout` (or point `REPOKIT_GH` at a missing file), then `repokit publish repokit-setup-check --publish-to github --no-push`. Log back in afterwards (`gh auth login`).
- [ ] **Expected:** exit 0; one line `GitHub: setup not run: gh is not logged in ... Once gh is ready: repokit publish ... finishes it`. No traceback.
- [ ] **Why this matters:** the setup must never make a publish fail.

## Section 1: offline checks (no GitHub)

### 1.1 The flags exist on all three verbs

- [ ] **Steps:** `repokit publish --help`, `repokit adopt --help`, `repokit create --help`
- [ ] **Expected:** each lists `--github-setup`, `--topics`, `--no-github-setup` with the same help text, naming both `--github` and `--publish-to github`.

### 1.2 Unknown step names are refused before anything is written

- [ ] **Steps:** `repokit create bad-steps --language generic --license mit --github-setup labels,bogus`
- [ ] **Expected:** exit non-zero; `unknown github-setup steps bogus; known: ...`; no `bad-steps` folder.

### 1.3 GitLab with --github-setup is refused before anything

- [ ] **Steps:** `repokit publish repokit-setup-check --publish-to gitlab --github-setup labels`
- [ ] **Expected:** exit non-zero; `--github-setup works with --publish-to github only`; nothing created on GitLab.

### 1.4 Topics are recorded for a later publish

- [ ] **Steps:** `repokit create topics-check --language generic --license mit --topics "cli, git,cli"`, then view `topics-check/.repokit.json` (cmd: `type`; PowerShell: `Get-Content`; POSIX: `cat`).
- [ ] **Expected:** `"topics": ["cli", "git"]` (trimmed, no repeat).

### 1.5 --no-github-setup beats the config

- [ ] **Steps:** with a `github_setup` list in the global config, `repokit publish repokit-setup-check --publish-to github --no-push --no-github-setup`
- [ ] **Expected:** no `GitHub:` lines at all.

## Section 2: the interactive prompt (MANUAL, a real terminal)

### 2.1 continue / skip / abort

- [ ] **Steps:** in a real terminal (not an agent, `CI` and `CLAUDECODE` unset, `REPOKIT_INTERACTIVE` unset), repeat HV.3 step 3 three times answering `s`, then `c`, then (on a fresh repository with a PR at #1) `a`.
- [ ] **Expected:**
  - The question reads `issues: #1 is already pull request '...', so Roadmap and Quick Notes would not be #1 and #2` then `[c]ontinue anyway, [s]kip this step, [a]bort the rest? [s]`.
  - `s` (or Enter): nothing created. `c`: Roadmap and Quick Notes created at the next numbers. `a` during a first publish (before the push): `stopped before the push`, nothing pushed, exit non-zero; running publish again pushes and finishes.
- [ ] **Check:** the prompt renders without garbled characters in cmd.exe (codepage 437) and PowerShell.

## Section 3: adopt

### 3.1 adopt --publish-to github runs the setup and still creates

- [ ] **Steps:** on a scratch folder with one committed file, `repokit adopt <folder> --publish-to github --private-repo --repo-name repokit-setup-check-adopt --token-command "gh auth token"`
- [ ] **Expected:** a new repository with #1/#2 and the labels; adopt never takes the update path even if the folder already had an `origin`.

## What the automated tests DON'T cover

- Real GitHub: the shared issue/pull-request numbering, Discussions on a private repository, the limit of three pinned issues, rate limits.
- The token route (`--publish-to`) and `gh` acting together on one repository, including an organization owner.
- The interactive prompt in a real terminal, and its rendering on Windows codepages.
- Dependabot opening a pull request after the first push (the reason for the window).

## Reporting issues found

1. Note the section and step.
2. Capture the exact command and output.
3. File an issue on DazzleTools/git-repokit referencing this checklist and 0.10.4.

## Cleanup

1. Delete the throwaway repositories yourself: `gh repo delete <you>/repokit-setup-check` (and `-pr`, `-adopt` if made). This needs the `delete_repo` scope (`gh auth refresh -s delete_repo`).
2. Delete the scratch folder (cmd: `rmdir /s /q %TEMP%\rk-0104`; PowerShell: `Remove-Item -Recurse -Force "$env:TEMP\rk-0104"`; POSIX: `rm -rf /tmp/rk-0104`).
3. Unset `REPOKIT_INTERACTIVE` if you set it (cmd: `set REPOKIT_INTERACTIVE=`; PowerShell: `Remove-Item Env:\REPOKIT_INTERACTIVE`; POSIX: `unset REPOKIT_INTERACTIVE`).
