# Human Test Checklist: every project guarded by git-repokit-common

**Target version:** 0.10.2
**Ships with commit:** TBD (v0.10.2: git-repokit-common for every project, configured from the branch model)
**Companion automated tests:** 37 new -- `tests/test_common_guard.py` (36) and `tests/test_packaging.py::test_repokit_version_matches_the_distribution` (1); `tests/test_new_default.py` rewritten for the new default. Full suite at ship: 398 passed, 14 skipped, 1 xfailed (with `tests/test_list_templates.py`, the release's other fix).

## What this is

0.10.2 makes git-repokit-common the default for every branch strategy and wires the private folders (`--private-dirs`, `--private-set`, the groups) into every guard: `.gitignore`, git-repokit-common's pre-commit, git-repokit's own pre-commit (the `--no-common` fallback), and `repokit safe-merge`. Before it, a folder named only by `--private-dirs` could reach a public branch, and a forced private file on a `github-flow` feature branch could be committed and pushed. This checklist is what a person runs to see each guard hold in a real project, and to judge the warning and the docs as they read.

## Prerequisites

1. git-repokit at this version on the path (`repokit --version`), git with `git subtree`, Python 3.10+.
2. A scratch folder, never inside a real repository, with git fenced to it and signing switched off **for these commands only** (never change global git config):

   **cmd.exe**:
   ```cmd
   mkdir %TEMP%\rk0102 && cd /d %TEMP%\rk0102
   set GIT_CEILING_DIRECTORIES=%TEMP%\rk0102
   set GIT_CONFIG_COUNT=2
   set GIT_CONFIG_KEY_0=commit.gpgsign
   set GIT_CONFIG_VALUE_0=false
   set GIT_CONFIG_KEY_1=tag.gpgsign
   set GIT_CONFIG_VALUE_1=false
   ```

   **PowerShell**:
   ```powershell
   New-Item -ItemType Directory -Force "$env:TEMP\rk0102" | Out-Null; Set-Location "$env:TEMP\rk0102"
   $env:GIT_CEILING_DIRECTORIES = "$env:TEMP\rk0102"
   $env:GIT_CONFIG_COUNT = "2"
   $env:GIT_CONFIG_KEY_0 = "commit.gpgsign"; $env:GIT_CONFIG_VALUE_0 = "false"
   $env:GIT_CONFIG_KEY_1 = "tag.gpgsign";    $env:GIT_CONFIG_VALUE_1 = "false"
   ```

   **POSIX**:
   ```bash
   mkdir -p /tmp/rk0102 && cd /tmp/rk0102
   export GIT_CEILING_DIRECTORIES=/tmp/rk0102
   export GIT_CONFIG_COUNT=2 GIT_CONFIG_KEY_0=commit.gpgsign GIT_CONFIG_VALUE_0=false GIT_CONFIG_KEY_1=tag.gpgsign GIT_CONFIG_VALUE_1=false
   ```
3. Every `repokit create` below adds `--license mit --no-push --user-name T --user-email t@example.com`; it is written as `<common>`.
4. Every git command names its repository with `-C`, so none can land in a real one. Files are written with `python -c`, which works in every shell.
5. **Reset between sections:** each section uses its own project name, so nothing needs resetting; the Cleanup section removes the scratch folder.

## High-Value Verification (~5 minutes)

### HV.1 -- A single-branch project keeps a `--private-dirs` folder off `main`

Validates: the hook's settings are written in a single-branch project, and `.gitignore` keeps the line.

- [ ] **Steps:**
  1. `repokit create hv1 --directories notes --private-dirs private,notes <common>`
  2. `git -C hv1 check-ignore -v notes/x.md`
  3. `python -c "open('hv1/notes/x.md','w').write('private\n')"`
  4. `git -C hv1 add -f notes/x.md`
  5. `git -C hv1 commit -m "a note"`
- [ ] **Expected:** step 2 names a `.gitignore` line `/notes/`; step 5 is refused with an error listing `notes/x.md` ("These files should only exist in private branches"). `git -C hv1 log --oneline -1` is not "a note".
- [ ] **Why this matters:** before 0.10.2 this commit went to `main`, the branch that gets pushed.

### HV.2 -- A `github-flow` feature branch is public

- [ ] **Steps:**
  1. `repokit create hv2 --branch-strategy github-flow <common>`
  2. `git -C hv2/github switch -c feature/login`
  3. `python -c "import os; os.makedirs('hv2/github/convos', exist_ok=True); open('hv2/github/convos/x.md','w').write('private\n')"`
  4. `git -C hv2/github add -f convos/x.md`
  5. `git -C hv2/github commit -m "forced"`
- [ ] **Expected:** step 5 refused, naming `convos/x.md`.
- [ ] **Why this matters:** feature branches in `github-flow` are pushed for pull requests; before 0.10.2 this commit passed and could be pushed.

### HV.3 -- `git add -f` still works on the private branch

- [ ] **Steps:**
  1. `python -c "import os; os.makedirs('hv2/local/convos', exist_ok=True); open('hv2/local/convos/x.md','w').write('private\n')"`
  2. `git -C hv2/local add -f convos/x.md`
  3. `git -C hv2/local commit -m "kept on private"`
- [ ] **Expected:** the commit succeeds (the person's deliberate override where private content belongs).

### HV.4 -- `--no-common` warns, and says what to do  *(human judgment)*

- [ ] **Steps:** `repokit create hv4 --branch-strategy simple --no-common <common>`
- [ ] **Expected:** a WARNING line starting `--no-common: git-repokit-common not added.`, saying the project gets git-repokit's basic pre-commit guard only, and naming `repokit setup-guardrails --vendor`.
- [ ] **Judge:** would a person who typed `--no-common` on purpose understand what they gave up, without feeling scolded? Would one who typed it by accident notice?

### HV.5 -- `repokit --version`

- [ ] **Steps:** `repokit --version`
- [ ] **Expected:** `RepoKit 0.10.2` (it printed 0.9.12 at 0.10.0 and 0.10.1).

## Section 1: git-repokit-common in every strategy

### 1.1 A private-branch strategy vendors it by default

- [ ] **Steps:** `repokit create s11 --branch-strategy standard <common>`
- [ ] **Expected:** `s11/local/scripts/repokit-common/` exists; `git -C s11/local log --oneline` shows "Configure git-repokit-common for the private-branch model"; `s11/github/scripts/repokit-common/` exists too (the public branch carries it).

### 1.2 The settings name the folders and branches

- [ ] **Steps:** `python -c "print(open('s11/local/.repokit-common.toml').read())"` (or `pyproject.toml` for a Python project)
- [ ] **Expected:** a `[tool.repokit-common]` table with `private-patterns` (including `CLAUDE.md`, `convos/`, `logs/`, `private/`, `revisions/`) and `private-branches` (`local`, `private`, `feature/*`, `feat/*`, `prototype/*`, `experiment/*`, `spike/*`). For a `github-flow` or `gitflow` project, `feature/*` and `feat/*` are absent.

### 1.3 Vendoring switched off warns the same way

- [ ] **Steps** (pick your shell):

  **cmd.exe**: `set REPOKIT_COMMON_SOURCE=off` then `repokit create s13 <common>` then `set REPOKIT_COMMON_SOURCE=`
  **PowerShell**: `$env:REPOKIT_COMMON_SOURCE = "off"; repokit create s13 <common>; Remove-Item Env:\REPOKIT_COMMON_SOURCE`
  **POSIX**: `REPOKIT_COMMON_SOURCE=off repokit create s13 <common>`
- [ ] **Expected:** a WARNING `git-repokit-common: vendoring switched off.` with the same explanation as HV.4; the create succeeds.

## Section 2: the other guards

### 2.1 safe-merge leaves the private folders out

- [ ] **Steps:**
  1. `repokit create s21 --branch-strategy simple --directories notes --private-dirs private,notes,convos,revisions,logs <common>`
  2. `python -c "import os; [os.makedirs(os.path.dirname(p), exist_ok=True) or open(p,'w').write('x\n') for p in ('s21/local/notes/x.md','s21/local/convos/x.md')]"`
  3. `git -C s21/local add -f notes/x.md convos/x.md` then `git -C s21/local commit -m "private work"`
  4. `git -C s21/local worktree add ../dev dev`
  5. From `s21/dev`: `repokit safe-merge private`
  6. `git -C s21/dev diff --cached --name-only`
- [ ] **Expected:** the staged list has neither `notes/x.md` nor `convos/x.md` (before 0.10.2 both were staged).

### 2.2 The `--no-common` hook knows the same folders

- [ ] **Steps:** as 2.1 with `--no-common` added to step 1 and only `notes/x.md` planted; after step 5, `git -C s22/dev commit -m "merge"`
- [ ] **Expected:** after step 5 `notes/x.md` **is** staged (safe-merge has no settings file to read; see `docs/Configuration.md`), and the commit is refused naming `notes/x.md`.

### 2.3 `--private-set enhanced` without a profile

- [ ] **Steps:** `repokit create s23 --private-set enhanced <common>`, then view `s23/.repokit-common.toml`
- [ ] **Expected:** `private-patterns` includes `credentials/`, `secrets/` and `local/`.

### 2.4 A setting you change is kept

- [ ] **Steps:**
  1. In `s11/local/.repokit-common.toml`, change `private-branches` to `["private", "scratch"]` and commit it on `private` (`git -C s11/local commit -am "my branches"`)
  2. From `s11/local`: `repokit setup-guardrails`
  3. View the file again
- [ ] **Expected:** `private-branches` is still `["private", "scratch"]`; repokit adds missing keys and never rewrites one you set.

## Section 3: the docs  *(human judgment)*

### 3.1 `docs/Configuration.md` reads right

- [ ] Read "Folders and private content" and "Committing private content on purpose".
- [ ] **Judge:** could a person who wants a folder kept private, or wants one private file committed anyway, find what to do in under a minute? Is it clear that `.repokit-common.toml` (or `pyproject.toml`'s table) is where to change it later, and that `git clean -fdx` deletes ignored private work?

## What the automated tests DON'T cover

- How the warnings read to a person (HV.4)
- A real `git push` of a refused branch to GitHub (the push gap was measured against a local bare remote; the fix stops the commit before any push)
- `git subtree` on a machine where it is missing (the vendoring-failure path is exercised only through `REPOKIT_COMMON_SOURCE=off`)
- The docs' clarity (Section 3)
- Linux and macOS: the creates were run on Windows; CI runs the suite on Linux
